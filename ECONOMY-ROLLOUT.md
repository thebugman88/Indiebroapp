# Brotherhood Coins and purchase recovery

This change is stacked on the security remediation branch. It is not a deployment and does not alter live Stripe prices. Merge the security foundation first. Keep this change in draft until the staging checklist below passes.

## Implemented offer

| Plan | Price (USD) | Monthly included BC | Uploaded-audio storage | Coin packs |
| --- | --- | --- | --- | --- |
| Free | $0 | 150 | 1 GB | $0.99 / 100 BC; $1.99 / 250 BC |
| Artist Pro | $14.99/month | 1,500 | 10 GB | $0.99 / 125 BC; $1.99 / 315 BC |

All existing tools and community features remain accessible without a paid tier. Cloud operations have explicit, server-enforced prices in `shared/economy.ts`. Local lyric editing, local OCR, community participation, basic audio measurements and local text counts do not spend Coins. Free cloud chat, quiz generation and practice opponents have disclosed daily allowances to bound provider costs. Technical abuse limits still apply.

Included Coins reset at 00:00 UTC on the first of the calendar month; there is no rollover. A Pro upgrade adds the difference between 150 and 1,500 to the current month's included allowance once. Repeated cancellation/re-subscription in a month cannot farm allowances. A downgrade preserves the already-granted allowance until the next monthly reset. Purchased and service-credit BC do not expire while the account is open. Included/earned BC are spent before non-expiring BC.

Storage extensions (+1 GB / 100 BC, +5 GB / 400 BC, +10 GB / 700 BC) are permanent account additions. Quota covers server-uploaded Judgment audio, not browser drafts. Over-quota accounts retain files and cannot upload further. Owners can delete uploaded tracks to free space. New uploads reserve quota before object storage; track creation and quota settlement commit atomically. Failed uploads are cleaned up, and reservations interrupted for an hour enter recovery before object deletion. Storage I/O itself still requires real Firebase Storage staging verification.

Earned BC are limited to 50 per calendar month: 5 once for a completed server-stored Judge profile and 5 per five validated reviews. Local XP cannot mint Coins. Referral payouts, general quest payouts, creator streak rewards, and the proposed distinct 15-BC second-pass Hit Analyzer are not implemented because no corresponding trusted server event/action exists yet. Do not advertise them as available.

## Purchase and recovery boundaries

- Purchase click opens the full terms and an unchecked acknowledgement. A separate final review requires a second unchecked confirmation. Stripe Checkout requires terms acceptance immediately before paying. The backend stores the terms version and acceptance time, checks the exact server price and authenticated account, and only fulfills Stripe-paid sessions with accepted consent and matching line items.
- Orders persist initiation, checkout processing, payment receipt, and fulfillment events in Firestore. Subscription invoices record initiation, processing, payment failures and receipt. Browser redirects are never proof of payment.
- Per-account request IDs and Firestore transactions prevent duplicate credits. One unresolved Pro checkout is allowed per account. Retrying an uncertain checkout reuses the same Stripe idempotency key and expiration. A completed/expired request must be explicitly reviewed again to start a new purchase.
- Every 60 seconds, an active server process checks pending orders against Stripe, looks for Checkout sessions created before a lost database acknowledgement, and retries delivery without charging again. It also restores stale AI reservations. Durable records survive restarts; the timer does not run while the server is stopped. Stripe webhooks retry failed writes. Monitor failures are surfaced in server logs. Keep an always-on process or invoke the authenticated administrator reconciliation endpoint from infrastructure.
- AI usage is reserved before processing. Failure restores the original balances once; an expired-month restoration goes to non-expiring BC. Successful JSON results are stored for owner-only recovery from Plan & Coins. Results too large for the persistence cap are not reported as delivered; their reservation is later restored. No model may invent payment status, mint Coins or deploy self-written billing code.
- Owners can request reconciliation. Verified administrators can repair a paid-but-undelivered Coin purchase with a single recorded service credit. Subscription exceptions require human review. Refund/dispute notifications prevent later re-delivery; available purchased Coins are reversed only for a previously delivered purchase. A spent-balance shortfall is flagged for review instead of silently making balances negative. Dispute resolution and subscription-refund access decisions need human review; they are not automatic policy decisions.
- The normal discretionary remedy is BC, not cash. The policy explicitly preserves non-delivery, duplicate/unauthorized charges, technical failure, misrepresentation, statutory rights and payment-provider requirements. Subjective dissatisfaction alone is not a discretionary-credit entitlement. AI accuracy and commercial results are not guaranteed. Required money refunds must be processed through the payment provider, not replaced with Coins. Obtain jurisdiction-specific legal review before launch. Stripe refund guidance: https://docs.stripe.com/refunds

## Staging release checklist

1. Configure Firebase Auth, Firestore Admin credentials and Storage using the same project as the browser Firebase settings. Deploy the deny-by-default rules and composite indexes in `judgement-zone`. Back up existing records. Before a new upload, existing owned audio without byte accounting is measured from Storage metadata and added transactionally to the wallet once; failed metadata reads block the upload. Verify this legacy migration in staging. Do not infer purchased balances or subscriptions from localStorage.
2. Create Stripe TEST prices: monthly recurring USD 1499 cents for `STRIPE_PRICE_ID_PRO`, one-time USD 99 cents for `STRIPE_PRICE_ID_COINS100`, and one-time USD 199 cents for `STRIPE_PRICE_ID_COINS250`. The server rejects mismatches. Configure the account's public terms URL as `https://YOUR-ORIGIN/api/legal/terms`, and set `APP_PUBLIC_URL` to that HTTPS origin. Review tax treatment before enabling collection; these sessions do not automatically enable Stripe Tax.
3. Configure a signed webhook at `/api/stripe/webhook` for `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `customer.subscription.created/updated/deleted`, `invoice.created/finalized/paid/payment_failed`, `charge.refunded`, and `charge.dispute.created`. Test retries and out-of-order notifications. Configure provider billing limits and monitoring separately.
4. Run `npm run check:staging`. It reports only presence/shape of configuration, not secret values. Then run verified Free/Pro sign-ins through both consent steps, Stripe success/cancel/decline, renewal, cancellation, Coin purchases, delivery recovery, AI failure, storage upload/delete, downgrade, and refunds/disputes using Stripe TEST mode. Test actual email verification and browser accessibility. No real charges are needed for this checklist.
5. Run `npm run lint`, `npm run test:security`, `npm run test:firebase` (Java 21+), `npm run build`, and `npm run test:production`. CI repeats these for main and the security-foundation PR base. Emulator tests use a demo project and never live credentials. Tests of Stripe use controlled responses, not actual live Stripe calls.
6. Review the costs of permanent storage and monthly AI allowances against actual provider usage. No profitability guarantee is implied. Complete legal/product review, then approve merge and deployment separately.
